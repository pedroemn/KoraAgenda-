 4. Por que SHA-256 isolado NÃO serve para senhas
========================================================================
a) Sem salt, a mesma senha gera sempre o mesmo hash:
   Ana   : 2c70dfbc967bd610fc7fbc6dfef0708a99d6be1fc44be3dffa47f0dde132442b
   Bruno : 2c70dfbc967bd610fc7fbc6dfef0708a99d6be1fc44be3dffa47f0dde132442b
   -> quem vê o banco sabe que os dois têm a mesma senha, e tabelas
      pré-calculadas (rainbow tables) quebram o hash na hora.

b) Ataque de dicionário contra o hash SHA-256 vazado:
   senha descoberta: 'senha1234' em 0.036 ms

c) Velocidade — quanto mais rápido, pior para senhas:
   SHA-256  :        530,394 tentativas/s (1 núcleo de CPU; GPUs fazem bilhões)
   Argon2id :           14.6 tentativas/s (e ~19 MiB de RAM por tentativa)
   -> Argon2id é ~36,239x mais caro por tentativa.
   Testar a lista rockyou (14,344,391 senhas) contra UM usuário:
      SHA-256  ~ 27.04 s
      Argon2id ~ 11.3 dias

   SHA-256 foi feito para ser RÁPIDO (integridade de arquivos, assinaturas).
   Senha precisa de função LENTA, com salt e custo ajustável (KDF de senha).

 5. Comparação segura (tempo constante) pela biblioteca
========================================================================
Código que valida a senha (app/core/security.py):

       def verify(self, password: str, stored_hash: str) -> bool:
           parsed = self._parse(stored_hash)
           if parsed is None:
               return False
           memory, iterations, lanes, salt, expected = parsed
           actual = self._derive(password, salt, memory, iterations, lanes, len(expected))
           # Comparação em tempo constante feita pela biblioteca padrão.
           return hmac.compare_digest(actual, expected)

hmac.compare_digest(iguais)     -> True
hmac.compare_digest(diferentes) -> False

-> `==` para no primeiro byte diferente: o tempo de resposta vaza
   quantos bytes estão certos (timing attack). `hmac.compare_digest`
   sempre percorre tudo, levando o mesmo tempo para qualquer entrada.
